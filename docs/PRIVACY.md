# Privacy and networking

The current application code contains no telemetry, analytics, update checks, advertising, crash uploads, remote-font lookup, or cloud-spelling client. Spelling uses a local Hunspell dictionary. A reviewed support-bundle and diagnostic-log implementation has not been built yet, so this repository makes no claim about such a facility.

The editor operates when Codex is absent or disabled. When the user opens the Codex panel, the application connects to the official Codex executable. Model, reasoning and speed choices remain visible. Opening the panel does not submit a document message; requested context may be processed by Codex/OpenAI when the user sends a message. Authentication uses app-server account methods and may open the user's browser; OwlDocs does not read Codex credential files or browser cookies.

Local application state includes document paths, optional chat history, and recovery checkpoints in a private SQLite database. A checkpoint now includes the complete original DOCX package, including opaque content the editor cannot display, alongside the editable semantic snapshot. Original packages are deduplicated by SHA-256, and source context is independently checksummed. Package and checkpoint updates are transactional. Saving or discarding a checkpoint removes its journal and any unreferenced package rows. The application does not upload these recovery packages; optional Codex tools receive the bounded semantic context described below.

For the current chat path, the Codex thread is requested with a read-only sandbox, approvals disabled, and an empty temporary working directory. After initialization, OwlDocs reads effective app-server configuration and constructs a thread override containing only inherited MCP server names with `enabled=false`; it applies that override on both start and resume and fails closed if it cannot verify the configuration shape. Server URLs, commands, headers, and environment values are not copied. The child receives an allowlisted environment and the packaged ChatGPT Codex binary is preferred over `PATH` when present. This is not a complete OS security boundary: read-only Codex mode can still permit filesystem reads outside that directory according to the installed runtime's sandbox behavior. The initial turn contains the user's message plus at most 12,000 characters each of current selection and document outline. Registered semantic read tools can subsequently return requested document chunks, bounded to 200,000 UTF-16 code units per call without splitting surrogate pairs. Document text is labeled as untrusted context.

The live `editor.v1` bridge supports bounded reads and creates revision-checked preview branches; only the desktop UI can accept a preview. Its capability tool describes the supported authoring subset without granting filesystem access. Model-supplied raster bytes and locally generated Excalidraw figures enter an isolated preview. Native scene JSON returned in a requested image read is document context sent through the same optional Codex connection. No file-capability tool is registered; legacy calls are denied. Save and PDF destinations in the current UI come only from native user file dialogs.

OS-level network denial for the GUI, renderer, and future MCP helper is a roadmap requirement, not an implemented guarantee. Every GUI file open is preflighted in the restricted parser worker, and the GUI reparses the same held descriptor rather than reopening the pathname when it builds the preservation model. Retained recovery packages receive the same restricted-worker validation before source-preserving recovery is enabled. That still leaves an in-process parser surface, so do not treat the present prototype as a complete security boundary for hostile files.
