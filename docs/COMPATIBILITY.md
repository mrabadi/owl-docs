# Compatibility matrix

This matrix describes the current executable foundation. “Preserved” means the original package data survives an unchanged Save As or a permitted local text patch; it does not imply that the editor can display or edit that feature. Exact unchanged Save As is additionally exercised against a reproducible 100-document public LibreOffice corpus. Editing claims remain limited to the explicit synthetic and targeted fixtures described below; this is not evidence of universal interoperability.

## Save modes

- **Unchanged imported Save:** does nothing when saving back to the same path.
- **Unchanged imported Save As:** writes the retained original package bytes. A synthetic test verifies byte identity even after the source path is removed, and the external corpus gate opened and copied 100/100 pinned public LibreOffice fixtures byte-for-byte.
- **Safe imported text patch:** changes only the character data of a mapped, eligible `w:t` span. The mapper rejects structural edits, signed packages, unsupported text contexts, unsafe whitespace changes, and invalid text. Tests verify unrelated XML and an opaque package member remain unchanged; the corpus runner can apply the same locality check to explicitly configured external fixtures.
- **Reopened supported document:** full regeneration is allowed only after preparing the imported semantic baseline with its original document defaults and proving coverage of every source member and its decompressed contents. The proof covers supported rich authoring, including equations and pictures, and rejects unrepresented custom parts, relationships, styles and settings. Redundant generated paragraph spacing equal to inherited source values is omitted for comparison; original XML is never normalized. Application insertion preferences do not replace source document defaults. Producer markers do not authorize a rewrite.
- **Simplified Save As:** after formatting or structural changes, the UI requires an explicit confirmation before writing the supported body subset—including paragraph-mark insertion formatting, native numbering, authored table structure, cell formatting, built-in styles, supported equations, and Picture Layout v1—and lists known categories that may be lost. It refuses the imported original path, aliases, and existing hard links as the destination.
- **New document save:** writes a macro-free Transitional DOCX containing body paragraphs with supported built-in `w:pStyle` identities, sparse direct `w:pPr/w:rPr` values and paragraph marks, native numbering definitions, authored native tables with the supported cell formatting and built-in styles, supported OMML equations, desktop-authored PNG/JPEG pictures in the Picture Layout v1 subset, deterministic used-style definitions and configured document defaults, plus a standard `settings.xml` default tab stop derived from the configured space-equivalent width. Separate engine/API tests also author and reopen ordered multiple sections; section authoring is not exposed by the desktop UI.

Older sequential multiline or wrapped header/footer parts retain their exact original
representation on unchanged copies and eligible body-text patches. If the
current independent regional layout cannot reproduce that native source,
header/footer, layout or structural edits require an explicitly approved
supported copy. The original file is never silently rewritten into the new
three-cell representation. Foreign or modified story tables outside the exact
supported structure remain on preservation paths.

Header/footer clipboard commands operate on the active region. A single selected
picture retains its existing native image payload and interoperable PNG/JPEG
fallback. Cut of mixed text/pictures or multiple pictures is guarded; select and
move one picture at a time. This boundary does not affect ordinary story text
or page-field editing.

The supported canvas/native header and footer edge distances are 36 pt
(720 twips), with a 6 pt gap to the body. Default 72 pt margins provide a minimum 30 pt
story region; measured content can reserve more body space. Narrow margins do
not discard or hide stories. Story expansion reserves at least 48 pt for the
body and bounds ordinary opposing stories to roughly half-page capacity. Custom imported DOCX header/footer edge distances remain on
preservation paths; the canvas uses the supported default anchors.

## Recovery compatibility

Native 0.6.0 documents retain their original built-in style catalog. The legacy
profile is selected only when the complete source styles part exactly matches
the frozen catalog for its used styles and original font defaults; a producer
label does not grant rewrite permission. Complete package reproduction remains
required. Applying a current heading to an older document writes the necessary
direct properties while keeping its older style definitions and appearance.

Semantic recovery uses version 16 when explicit table geometry or cell layout is present, version 15 for table-cell pictures alone, and version 14 otherwise. Layout, object identities and original image bytes are retained, and older payload versions remain readable. SQLite recovery journals remain schema 14 and separately retain the exact original package in a SHA-256 keyed binary store. Source context is independently checksummed and journal/source updates are transactional. Recovery reparses retained bytes through the restricted worker and reconstructs the original baseline and source mappings; it does not depend on the source pathname still existing or containing the same file. Safe recovered text patches preserve opaque parts when saved to a different destination. Legacy semantic-only checkpoints remain recoverable as supported copies. Missing or corrupt retained source data is diagnosed and never silently treated as lossless recovery.

Saves validate their candidate before the atomic rename and recheck destination content immediately before commit. Timestamp-only changes do not cause false conflicts. A completed rename followed by a failed directory durability sync is reported as saved with a warning. The editor retains the validated committed bytes as its next conflict baseline, avoiding a post-save pathname replacement race.

## Optional Codex protocol compatibility

OwlDocs 0.6.5 uses the `editor.v1.catalog.10` tool contract. Its capability
catalog describes the supported authoring subset and operation schemas;
reads include body blocks, tables/cells, notes, default header/footer stories,
images, page settings and current selection context. Authoring proposals use
revision-checked native operations, including editable Excalidraw creation and
native scene patches, table/picture editing, formatting, lists, single-section
geometry and academic objects. Combined content and page geometry accept and
undo as one transaction. Page settings carry a separate opaque read token
because changing margins does not increment the core text revision.

The agent cannot accept its own preview or save, open, export or browse files
through these tools. Application preferences and unsupported Word structures
are outside this document-authoring API. Raster tool input is limited to 4 MiB
per preview; this transport limit is narrower than desktop insertion limits.
Native figure context is bounded and explicitly reports completeness. A native
patch applies only to named elements of the embedded authoritative scene and
preserves untouched native objects. Replacing an entire figure is an explicit
reconstruction operation. See `CODEX_AUTHORING.md` for exact boundaries.

The catalog version is stored with a document thread binding. After an upgrade
that changes tools or built-in guidance, OwlDocs creates a fresh document
thread instead of resuming a binding with stale dynamic tools. Existing saved
conversation history is retained; the experimental runtime does not support
replacing dynamic tools on `thread/resume`.

The `editor.v1` dynamic tools use an experimental `codex app-server` surface. OwlDocs sends `capabilities.experimentalApi=true` in `initialize`, reads the effective configuration, and disables every inherited MCP server by name in the per-thread config applied to both `thread/start` and `thread/resume`. Only then does it register the document tools. Invalid or incompatible configuration fails closed before authentication/model discovery. A fake-process controller test fixes this ordering and verifies that URLs, commands, and other server details are never copied into the override. When both Codex and Python are installed at configure time, an additional CTest check generates the installed runtime schema and requires the capability, configuration, dynamic-tool, and tool-call fields used by OwlDocs. That optional check is absent on offline hosts without those executables and is not a general compatibility guarantee. An absent or incompatible Codex runtime affects only optional chat; the editor remains usable offline.

Every release should expand this table only from corpus and round-trip evidence. A green unit-test suite is not evidence of universal Word parity.

Supported paragraph-mark `w:pPr/w:rPr` properties are part of the editable basic body subset. Unknown or unsupported direct `w:pPr`/`w:rPr` properties are reported as compatibility warnings and prevent a document from being classified as a fully basic body. Their original XML remains on preservation paths.
